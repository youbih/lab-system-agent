> 目标：把当前“单次问答”升级为有状态、可调用工具、可人工确认的 Agent；并增加预约开始前的短信提醒

## 第零章 当前基线

| 能力 | 当前实现 |
|---|---|
| AI 对话 | `POST /api/ai/chat`，单次调用大模型，无状态 |
| 数据访问 | 模型查不到数据库，只能解释规则 |
| 写操作 | 模型不能创建、取消、审核预约 |
| 对话记忆 | 前端每次传完整历史，后端不保存 |
| 通知 | 没有短信、邮件、站内信 |
| Redis | 暂未使用 |
| 定时任务 | 无；过期清理是“打开列表时惰性清理” |

本文件规划两条升级线：

1. **LangGraph**：让 AI 从“说明书”变成“能查数据、能生成操作草稿的预约助理”
2. **短信提醒**：在预约开始前 20 分钟通知学生，并引入 Redis 处理幂等、锁、延迟任务

两条线可以独立落地，也可以共享 Redis 基础设施。

## 第二章 Redis 在整体架构中的角色

Redis 不只是“缓存”，在这个系统里可以承担六类职责：

| 用途 | 数据结构 | 说明 |
|---|---|---|
| 分布式锁 | `SET key value NX PX` | 多实例部署时，保证同一时间只有一个实例处理同一条预约提醒 |
| 幂等键 | `SETNX` + TTL | 防止重复发短信、重复执行审核 |
| 延迟队列 | ZSET（score 为执行时间戳） | 自己实现“到点执行”的提醒任务 |
| 限流 | `INCR` + `EXPIRE` | 限制单用户/单 IP 的 AI 调用次数、短信发送频率 |
| LangGraph 会话 | Redis Checkpointer | 保存对话状态，按 `thread_id` 恢复 |
| 任务队列 Broker | Celery + Redis | 异步发送短信、执行耗时任务 |
| 事件流（可选） | Redis Stream | 通知事件分发，未来可替换为 Kafka/RabbitMQ |

### 2.1 推荐的 Key 命名

```text
lock:reminder:{reservation_id}
idempotent:reminder:{reservation_id}:sms
rate:ai:{user_id}:{yyyyMMdd}
delay:reminder                 # ZSET
checkpoint:ai:{thread_id}      # 由 LangGraph checkpointer 管理
```

约定：

- 统一前缀，方便排查
- 锁必须设置过期时间，避免死锁
- 幂等键的 TTL 要覆盖业务窗口（例如 7 天）
- 不要使用 `KEYS *`，用 `SCAN` 或明确的 key
- 生产环境区分 Redis DB 或实例，避免和 Celery 互相影响

### 2.2 不建议用 Redis 做的事情

- **不要当主数据库**：预约、用户、通知记录仍以 MySQL 为准
- **不要用它保存唯一的业务真相**：Redis 丢数据时，业务要能从 MySQL 恢复
- **不要用 `FLUSHALL` 清理测试数据**：会误删共享实例的数据

## 第三章 LangGraph 升级方案

### 3.1 现状与目标

| 能力 | 当前 | 目标 |
|---|---|---|
| 对话 | 单轮/多轮文本 | 有状态、可恢复的多轮 |
| 数据 | 不可查 | 通过工具查询 |
| 操作 | 不可写 | 生成草稿，确认后执行 |
| 流程 | 一次模型调用 | 多节点、条件分支、循环追问 |
| 记忆 | 前端传历史 | Checkpointer 持久化 + 可选长期记忆 |
| 输出 | 一次性返回 | 流式输出 |
| 可观测 | 日志 | LangSmith / 自己记录节点轨迹 |

### 3.2 核心概念

| 概念 | 作用 |
|---|---|
| `StateGraph` | 定义整张流程图 |
| State | 在节点之间传递的数据，例如 `messages`、`user_id`、`intent`、`draft` |
| Node | 一个处理步骤，例如“识别意图”“查询设备”“生成草稿” |
| Edge | 节点之间的连线 |
| Conditional Edge | 根据条件走不同分支 |
| ToolNode | 执行工具调用的节点 |
| Tool | 包装现有 service 的函数，例如查预约、创建预约 |
| Checkpointer | 保存每一步状态，按 `thread_id` 恢复 |
| `interrupt` | 暂停图，等待用户确认后继续 |
| `astream_events` | 流式输出节点事件和 token |

### 3.3 预约助手的图设计

```text
START
  ↓
[识别意图]
  ↓
  ├── 闲聊/规则问答 → [直接回答] → END
  ├── 查询类 → [调用查询工具] → [总结结果] → END
  └── 创建预约 → [抽取参数]
                     ↓
               参数完整？──否──→ [追问缺失信息] → 回到抽取
                     │是
                     ↓
              [规则校验：时间/实验室/设备]
                     ↓
              [查询冲突]
                     ↓
                有冲突？──是──→ [推荐替代时段] → 回参数确认
                     │否
                     ↓
              [生成预约草稿]
                     ↓
              [interrupt：等待用户确认]
                     ↓
                确认？──否──→ END
                     │是
                     ↓
              [调用 create_reservation 工具]
                     ↓
              [返回预约结果] → END
```

取消预约、管理员审核可以做成类似的子图。

### 3.4 工具清单

工具要包装现有 service，并在内部做权限校验：

| 工具 | 作用 | 权限 |
|---|---|---|
| `query_labs` | 查询实验室列表/开放时间/状态 | 登录用户 |
| `query_equipments` | 按实验室查设备 | 登录用户 |
| `query_my_reservations` | 查询当前用户预约 | 仅本人 |
| `check_availability` | 检查时段是否冲突 | 登录用户 |
| `create_reservation` | 创建预约 | 登录用户，必须确认 |
| `cancel_reservation` | 取消自己的待审核预约 | 仅本人，必须确认 |
| `query_pending_reservations` | 查询待审核列表 | 仅管理员 |
| `audit_reservation` | 通过/拒绝 | 仅管理员，必须确认 |

关键原则：

- **工具参数由代码校验**，不能信任模型生成的 `user_id`
- `current_user` 由后端注入，不放进模型可修改的参数里
- 写操作工具必须校验当前状态（例如只能审核待审核记录）

### 3.5 人工确认

LangGraph 的 `interrupt` 可以把“准备执行”与“真正执行”分开：

```text
模型生成草稿
    ↓
后端保存草稿到状态
    ↓
interrupt 暂停，返回草稿卡片给前端
    ↓
用户点击“确认”
    ↓
前端带 thread_id 调用 /confirm
    ↓
LangGraph 从断点恢复，执行写操作
```

需要注意：

- 草稿不能只存在模型上下文里，要存在状态/数据库
- 确认接口要幂等，防止连点两次
- 取消、审核同样要确认
- 用户修改参数后要重新校验，而不是直接沿用旧草稿

### 3.6 记忆与会话

| 层次 | 方案 | 说明 |
|---|---|---|
| 单次请求 | State | 节点之间共享 |
| 对话内 | Checkpointer（Redis/MySQL） | 按 `thread_id` 恢复多轮状态 |
| 长期 | MySQL 会话/消息表 | 支持历史列表、审计 |
| 缓存 | Redis | 热会话、限流、锁 |

`thread_id` 建议由前端生成或后端按“用户 + 会话”生成，例如：

```text
thread_id = f"user-{user_id}:{conversation_id}"
```

如果使用 `langgraph-checkpoint-redis`，需要单独评估它和当前 `openai==3.14.1`、Python 版本的兼容性。

### 3.7 API 设计建议

| 接口 | 作用 |
|---|---|
| `POST /api/ai/chat` | 非流式对话，返回最终文本或草稿 |
| `GET /api/ai/chat/stream` | SSE 流式输出 |
| `POST /api/ai/chat/confirm` | 确认执行草稿 |
| `GET /api/ai/conversations` | 会话列表（可选） |
| `GET /api/ai/conversations/{id}` | 历史消息（可选） |

请求中需要带：

- `thread_id` / `conversation_id`
- `messages`（或由后端从会话恢复）
- 确认接口需要 `draft_id` 或 `interrupt_id`

### 3.8 前端配合

- 保存 `thread_id`，刷新页面后恢复对话
- 支持流式显示（SSE / fetch stream）
- 写操作展示“草稿卡片”：实验室、设备、时间、状态
- 确认/取消按钮调用确认接口
- 显示工具调用状态，例如“正在查询设备…”
- 出错时区分“模型回答失败”和“业务校验失败”

### 3.9 安全边界

- 模型只能调用白名单工具
- 工具内部做权限和状态校验
- 写操作必须人工确认
- 记录审计日志：谁、什么会话、执行了什么
- 防止提示词注入：工具参数必须结构化校验，不能执行模型生成的 SQL
- 控制上下文长度，工具结果只返回必要字段
- 限制调用频率和每日额度

### 3.10 分阶段落地

| 阶段 | 内容 | 验收 |
|---|---|---|
| 1 | 把查询类 service 包装成工具，做只读 Agent | 能查实验室、设备、我的预约 |
| 2 | 加意图路由、参数抽取、缺参追问 | 不完整请求会反问 |
| 3 | 加预约草稿和 `interrupt` 确认 | 确认后才写库 |
| 4 | 加取消、审核子图 | 权限和状态校验正确 |
| 5 | 加 Checkpointer、流式输出 | 刷新可恢复，前端流式显示 |
| 6 | 加 RAG、多 Agent、推荐 | 回答更准确，复杂任务可拆解 |

### 3.11 风险

- 模型选错工具或参数 → 需要结构化输出和重试策略
- 工具调用链路过长 → 延迟和成本上升
- 会话状态膨胀 → 需要摘要和截断
- 写操作误执行 → 必须确认 + 幂等 + 权限
- 依赖版本冲突 → 锁定 `langgraph`、`langchain-openai`、`openai` 版本并测试

## 第四章 短信提醒方案

### 4.1 目标与规则

- 预约开始前 **20 分钟**发送提醒
- 只提醒 **已通过(1)** 的预约
- 待审核、已拒绝、已取消、已过期不提醒
- 已取消/已改期的预约要能撤销提醒
- 同一预约只提醒一次
- 手机号缺失或无效时记录失败，不阻塞主流程

### 4.2 流程

```text
管理员审核通过
    ↓
预约进入“待提醒”
    ↓
定时扫描 / 延迟任务
    ↓
检查：status 仍为 1？start_at - now 是否为 20 分钟？
    ↓
检查：用户手机号有效？是否已提醒过？
    ↓
抢锁 → 发送短信 → 写通知记录
    ↓
成功 / 失败重试 / 告警
```

### 4.3 技术栈

| 职责 | 课程阶段 | 生产阶段 |
|---|---|---|
| 定时 | APScheduler，每分钟 | Celery Beat |
| 队列 | 无 | Celery + Redis |
| 锁/幂等 | MySQL 唯一索引 | Redis `SET NX PX` + 唯一索引 |
| 短信 | 阿里云/腾讯云 SDK | 同左，加多通道降级 |
| 记录 | MySQL `notification_log` | 同左 |
| 监控 | 日志 | Sentry + Prometheus + 告警 |
| 配置 | `.env` | 密钥管理服务 |

### 4.4 触发方式对比

| | 方案 A：轮询扫描 | 方案 B：延迟任务 |
|---|---|---|
| 实现 | 每分钟查一次窗口 | 审核通过时投递延迟任务 |
| 精度 | 最多 1 分钟误差 | 精确到秒 |
| 复杂度 | 低 | 中高 |
| 撤销 | 不需要 | 取消时要撤销任务 |
| 重启恢复 | 天然支持 | 需要补偿机制 |
| 适用 | 课程、小规模 | 大规模、要求精确 |

推荐：**先 A 后 B**。

### 4.5 通知记录表

```text
notification_log
- id
- reservation_id
- user_id
- type            reminder / cancel / audit
- channel         sms / email / in_app
- status          pending / sent / failed
- provider_msg_id
- error
- sent_at
- create_time
- update_time
```

唯一索引：

```text
(reservation_id, type, channel)
```

这样即使任务重复执行，也只会产生一条记录。

### 4.6 幂等与并发

三层保护：

1. **数据库唯一索引**：最终兜底
2. **Redis 幂等键**：`SET idempotent:reminder:{id} 1 NX EX 604800`
3. **分布式锁**：`SET lock:reminder:{id} {uuid} NX PX 60000`

流程：

```text
尝试获取锁
  ↓ 成功
插入 notification_log（唯一索引）
  ↓ 成功
调用短信服务
  ↓
更新记录为 sent / failed
  ↓
释放锁
```

如果获取锁失败，说明别的实例正在处理，直接跳过。

### 4.7 Redis 具体用法

**分布式锁（示意）**

```text
SET lock:reminder:123 <uuid> NX PX 60000
```

释放时最好用 Lua 校验 value，避免误删别人的锁。

**延迟队列（方案 B）**

```text
ZADD delay:reminder <start_at - 20min 的时间戳> <reservation_id>
```

消费者定时 `ZRANGEBYSCORE` 取出到期任务，处理成功后 `ZREM`。

**限流**

```text
INCR rate:sms:{user_id}:{yyyyMMdd}
EXPIRE rate:sms:{user_id}:{yyyyMMdd} 86400
```

超过阈值就跳过并记录。

### 4.8 短信服务商接入

国内常用：阿里云短信、腾讯云短信。

需要准备：

- 企业实名认证
- 短信签名（例如“XX实验室”）
- 模板审核，例如：

```text
【XX实验室】您预约的{1}将于{2}开始，请提前到场。如需取消请登录系统操作。
```

- AccessKey / Secret 放在 `.env` 或密钥管理服务
- 发送频率限制、余额告警

注意：

- 模板变量不能随意拼接
- 短信内容避免包含过多个人信息
- 用户应知情并可选择关闭提醒
- 记录服务商返回的 `msg_id` 和错误码

### 4.9 失败重试

- 网络错误、限流：指数退避重试 2~3 次
- 手机号无效、模板错误：不重试，记录原因
- 余额不足：告警，暂停任务
- 所有失败都要能在管理端或日志中查询

### 4.10 边界情况

| 情况 | 处理 |
|---|---|
| 审核通过时距开始不足 20 分钟 | 剩余 > 5 分钟则立即补发，否则跳过并记录 |
| 提醒前预约被取消 | 扫描时检查状态，不是 1 就不发 |
| 用户手机号为空 | 记录 failed，不重试 |
| 同一预约重复扫描 | 唯一索引 + 锁 |
| 服务重启 | 轮询方案天然恢复；延迟队列需要补偿扫描 |
| 多实例部署 | 锁或数据库抢占 |
| 时区 | 统一使用 `Asia/Shanghai` |
| 短信服务商故障 | 重试、降级到站内信/邮件、告警 |

### 4.11 监控指标

- 每分钟待提醒数量
- 发送成功率、失败率
- 平均发送耗时
- 重试次数
- 服务商余额
- 重复发送次数（应为 0）

### 4.12 分阶段落地

| 阶段 | 内容 |
|---|---|
| 1 | APScheduler + 短信 SDK + `notification_log` |
| 2 | 唯一索引 + 失败重试 + 管理端查看记录 |
| 3 | 引入 Redis 锁和幂等键，支持多实例 |
| 4 | 改用 Celery + Redis 延迟任务 |
| 5 | 增加站内信、邮件、用户提醒偏好 |

## 第五章 统一通知事件设计

短信只是渠道之一。建议把“预约状态变化”抽象成事件，避免每加一个渠道就改业务代码。

### 5.1 事件类型

```text
reservation.created
reservation.approved
reservation.rejected
reservation.cancelled
reservation.expired
reservation.reminder_due
```

### 5.2 实现方式

阶段一：在 service 里写完业务后，直接调用通知服务（简单，但耦合）。

阶段二：使用 **Transactional Outbox**：

1. 业务事务里同时写入 `outbox_event` 表
2. 后台 worker 轮询 outbox，投递到 Redis Stream / MQ
3. 通知消费者按事件发送短信/站内信
4. 成功后标记 outbox 已处理

好处：

- 业务事务和通知解耦
- 不会因为短信服务故障导致预约事务回滚
- 支持重试和补偿

### 5.3 渠道扩展

| 渠道 | 说明 |
|---|---|
| 站内信 | 最便宜，前端轮询或 WebSocket |
| 邮件 | 适合详细通知 |
| 短信 | 到达率高，有成本 |
| 微信/企业微信 | 需要额外接入 |

## 第六章 里程碑路线图

| 里程碑 | 目标 | 关键技术 | 验收标准 |
|---|---|---|---|

## 第九章 风险与原则

### 9.1 原则

1. **模型只负责理解和表达，不负责权限和最终决策**
2. **写操作必须确认，且由后端再次校验**
3. **MySQL 是业务真相，Redis 是加速和协调**
4. **所有外部调用都要有超时、重试、日志**
5. **通知失败不能影响预约主流程**
6. **任何新渠道都通过事件接入，而不是改业务代码**

### 9.2 主要风险

- 版本兼容：LangGraph / LangChain / openai 的版本组合
- 成本：长对话、流式输出、工具循环都会增加 token
- 延迟：多节点串行调用会变慢
- 误操作：模型生成错误参数，必须靠校验和确认兜底
- 数据一致性：Redis 与 MySQL 的边界要清晰
- 合规：短信签名、模板审核、用户知情同意

## 第十章 企业级改造清单（面试导向）

本章是对整个项目的长期改造清单。目标不是“堆技术”，而是让项目具备：

> 可维护、可测试、可观测、可回滚、安全、能应对并发和故障。

每一项都建议按“问题 → 方案 → 取舍 → 验证”的方式整理，方便面试时讲清楚。

### 10.1 优先做：基础工程化

这些是课程项目和工程项目差距最大的地方，性价比最高。

#### 10.1.1 数据库迁移：Alembic

现状：`Base.metadata.create_all` + 手写 `ALTER TABLE`。

改造：

- 用 Alembic 管理表结构版本
- 每次变更生成 migration，可升级、可回滚
- CI 检查“模型定义与 migration 是否一致”

面试可问：

- 线上给大表加字段，怎么做到低风险？
- 加可空列、分批回填、双写、灰度分别解决什么问题？
- migration 执行失败怎么回滚？

#### 10.1.2 自动化测试

现状：几乎没有测试。

改造：

- `pytest` + `TestClient` / `httpx`
- 每个测试用事务回滚或独立测试库
- 覆盖：预约冲突、取消、审核、过期、越权访问、并发
- 设置覆盖率门槛

面试可问：

- 怎么测并发冲突？
- 怎么测水平越权和垂直越权？
- 测试数据怎么隔离？

#### 10.1.3 CI/CD

- GitHub Actions：`ruff`、`mypy`、`pytest`、前端 build
- `pre-commit` 做格式与静态检查
- 坏代码不能进入主分支

面试可问：

- 你们的发布流程是什么？
- 如何避免带病上线？

#### 10.1.4 Docker 化

- `Dockerfile` + `docker-compose`
- 一键启动 backend、MySQL、Redis、frontend
- 数据卷、环境变量、健康检查

面试可问：

- 镜像怎么分层？
- 配置怎么注入？
- 数据怎么持久化？

#### 10.1.5 结构化日志与请求追踪

- 每条日志带 `request_id / trace_id`、用户 ID、耗时
- 统一格式，接入 Loki/ELK

面试可问：

- 线上一个请求报错，怎么快速定位？
- 日志里哪些信息不能打？

#### 10.1.6 错误码体系

现状：业务错误统一 `code=500`。

改造：

- 区分参数错误、权限错误、资源不存在、状态冲突、限流、第三方失败
- 前端按错误码做不同处理
- 保留 HTTP 状态码和业务码的映射关系

面试可问：

- 为什么 HTTP 200 里还要放业务错误码？

### 10.2 并发与一致性

#### 10.2.1 预约超卖

现状：先查冲突再插入，并发时两个请求可能都通过。

方案对比：

| 方案 | 做法 | 取舍 |
|---|---|---|
| 数据库唯一约束 | 对可唯一化的字段建唯一键 | 简单，但时间区间重叠无法直接约束 |
| 悲观锁 | `SELECT ... FOR UPDATE` 锁实验室/设备行 | 可靠，锁粒度大、吞吐低 |
| 乐观锁 | 版本号 + 重试 | 适合冲突少的场景 |
| Redis 分布式锁 | `SET NX PX` | 快，但要处理续期、误删、脑裂 |
| 串行化隔离级别 | 数据库保证 | 易死锁、性能差 |

面试可问：

- 为什么选这个方案？代价是什么？
- 失败后怎么重试？重试几次？

#### 10.2.2 幂等设计

- 创建预约：`Idempotency-Key` + 唯一键
- 审核/取消：`UPDATE ... WHERE status=0` 看影响行数
- 通知：`notification_log` 唯一索引

面试可问：

- 用户连点两次提交会发生什么？怎么防止？

#### 10.2.3 缓存设计（Redis）

适合缓存：实验室列表、设备列表、开放时间、热门查询。

必须能回答：

- 穿透：空值缓存、布隆过滤器
- 击穿：互斥锁、逻辑过期
- 雪崩：随机 TTL、多级缓存
- 一致性：先更新数据库再删缓存、延迟双删、订阅 binlog

面试可问：

- 缓存和数据库不一致怎么办？

#### 10.2.4 限流与防刷

- 登录防爆破
- AI 接口按用户限流
- 短信发送频率限制
- Redis + Lua 令牌桶/滑动窗口，或 Nginx 层限流

面试可问：

- 怎么设计一个分布式限流器？

#### 10.2.5 异步任务与消息队列

- Celery/RQ + Redis：短信、邮件、报表、图片处理
- 重试、死信队列、任务幂等
- 事件驱动：预约状态变更
- Transactional Outbox：业务事务和通知解耦

面试可问：

- 消息丢了怎么办？重复消费怎么办？

### 10.3 安全

#### 10.3.1 JWT 完整方案

- 短期 access token + 长期 refresh token
- 注销/封禁：黑名单或 token 版本号
- 密钥轮换
- 固定算法，防止 `alg=none`

面试可问：

- JWT 怎么注销？
- 放在 localStorage 有什么风险？
- XSS 和 CSRF 分别怎么防？

#### 10.3.2 RBAC 权限模型

现状：`role != "admin"` 硬编码。

改造：

- 用户、角色、权限三张表
- 权限点：`reservation:audit`、`equipment:update`
- 统一鉴权依赖/装饰器

面试可问：

- 如何设计一个可扩展的权限系统？

#### 10.3.3 越权与安全测试

- 水平越权：改 URL 里的预约 ID 看别人的记录
- 垂直越权：学生调用管理员接口
- 文件上传：类型、大小、魔数、路径穿越、病毒扫描
- 密码：bcrypt/argon2、失败锁定、验证码
- 依赖漏洞：`pip-audit`、Dependabot

面试可问：

- 你做过哪些安全检查？
- 文件上传有哪些风险？

#### 10.3.4 敏感数据与合规

- 手机号、邮箱脱敏展示
- 日志不打印完整手机号和 token
- 需要时加密存储（AES-GCM）

面试可问：

- 日志里能不能打用户手机号？
- 个人信息保护要注意什么？

### 10.4 可观测性与稳定性

#### 10.4.1 监控指标

- QPS、P50/P95/P99 延迟、错误率
- 数据库连接池、慢查询
- Redis 命中率、内存
- 队列积压

面试可问：

- 系统变慢，你怎么排查？

#### 10.4.2 追踪与告警

面试可问：

- 如何设计告警，避免告警风暴？

#### 10.4.3 高可用

- 多实例 + 健康检查 `/health/live`、`/health/ready`
- 优雅停机
- 数据库主从、Redis 哨兵/集群（可选）
- 备份与恢复演练，明确 RPO/RTO

面试可问：

- 发布时如何做到不中断？

### 10.5 数据与性能

#### 10.5.1 索引与 SQL 优化

## 附录：参考实现顺序（建议）

1. 先把现有 `services` 抽成可复用工具层（不依赖 LLM）
2. 用 LangGraph 做只读查询图，验证工具调用
